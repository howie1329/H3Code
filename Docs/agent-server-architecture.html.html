H3Code Agent Server Architecture

Status: Active (PI via WS)  ·  Last updated: May 2026  ·  Supersedes (in spirit): direct Electron IPC → PI subprocess

H3Code is evolving from a PI-specific desktop shell into a layered system: UI → Server → Provider layer → actual provider, with the desktop app talking to a local Agent Server over WebSockets. PI Agent remains the first provider; Codex Server and Cursor follow.

1. Summary

H3Code Desktop will treat a local Agent Server as the single integration point for agent backends. The Svelte UI connects via WebSocket; the server orchestrates workspaces, connections, platform services (git, worktrees, preferences), and delegates agent behavior to pluggable providers.

┌─────────────────────────────────────────────────────────────────┐ │ UI (Svelte / Electron renderer or future web client) │ │ · Workspace chrome · Transcript · Composer · Settings │ │ · Session read model (projector over domain events) │ └───────────────────────────────┬─────────────────────────────────┘ │ WebSocket (JSON messages) ▼ ┌─────────────────────────────────────────────────────────────────┐ │ Agent Server (Node) │ │ · Connection manager · Workspace / prefs · Git / worktrees │ │ · Provider registry · Auth to local server only │ └───────────────────────────────┬─────────────────────────────────┘ │ AgentProvider interface ▼ ┌─────────────────────────────────────────────────────────────────┐ │ Provider layer │ │ ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ │ │ │ PiProvider │ │ CodexProvider│ │ CursorProvider│ … │ │ └──────┬───────┘ └──────┬───────┘ └──────┬───────┘ │ └─────────┼─────────────────┼─────────────────┼──────────────────┘ ▼ ▼ ▼ pi --mode rpc Codex Server API Cursor API / CLI
Product boundary unchanged Providers own sessions, messages, tools, models, and runtime behavior. H3Code does not become the source of truth for transcripts.

2. Goals and non-goals

Goals

  • Support multiple agent backends without PI-shaped types leaking into the UI.
  • Run agent integration in a dedicated Agent Server process, reachable via WebSocket.
  • Reuse the existing SessionDomainEvent → projector → read-model path in the UI where possible.
  • Ship PI first (parity with today), then Codex Server, then Cursor.
  • Keep platform concerns (SQLite metadata index, git diff, worktrees, repo picker) in the server, not in each provider.
  • Enable future clients (desktop, local web, automation) against the same server API.

Non-goals (this architecture pass)

  • Cloud sync, accounts, teams, or multi-user server deployment.
  • H3Code-owned transcript or session persistence (beyond metadata indexing for discovery).
  • Forcing Codex or Cursor to expose PI-identical RPC commands.
  • Full-text search or transcript indexing in SQLite.

3. Current state

Today the desktop app uses a flat stack:

Svelte renderer → preload IPC → Electron main (~1.3k LOC) → pi --mode rpc (JSONL)
  • IPC channels and window.h3code types are PI-specific (PiSessionState, pi:connect-repo, etc.).
  • @earendil-works/pi-coding-agent RPC types are used directly in the main process.
  • src/lib/pi-session/ already maps PI RPC events → SessionDomainEvent → UI read model (keep this pattern; move PI mapping into PiProvider).
  • Git, worktrees, and SQLite preferences live in Electron main alongside RPC.

The refactor extracts the main process’s agent and orchestration logic into a standalone server and replaces IPC with WebSocket for the UI boundary. Electron becomes a host: window management, native dialogs, optional process supervision for the server.

4. Target architecture

4.1 Desktop deployment

┌──────────────── Electron ────────────────┐ │ Main: spawn Agent Server, native FS │ │ Renderer: Svelte UI ──WebSocket──► │──────► localhost:PORT/ws └────────────────────────────────────────┘ │ ▼ ┌─────────────────┐ │ Agent Server │ └─────────────────┘

The server binds to localhost only by default. The desktop app starts the server on launch (or connects to an existing instance in dev). Native affordances (directory picker, reveal in Finder, executable picker) may remain as a thin Electron bridge until the server exposes equivalent hooks or the UI handles them locally.

5. Layer responsibilities

Layer Owns Must not own
UI Rendering, routing, composer UX, session read model projection, capability-gated controls, optimistic UI where appropriate Subprocess spawn, RPC framing, provider protocols, canonical message store
Agent Server WebSocket sessions, connection lifecycle, provider selection per workspace, preferences / SQLite metadata index, git diff and worktree inventory, merging indexed sessions with provider-native session lists Provider-specific wire formats; duplicating full transcripts
Provider layer AgentProvider implementations, capability advertisement, translation to SessionDomainEvent, provider-native session refs Global UI state; cross-provider workspace policy (server decides)
Actual provider PI subprocess, Codex Server process/API, Cursor integration H3Code product rules (documented here and in MVP brief)

5.1 AgentProvider interface (conceptual)

interface AgentProvider {
  readonly id: "pi" | "codex" | "cursor" | string;
  readonly capabilities: ProviderCapabilities;

  connect(ctx: ConnectContext): Promise<ProviderConnection>;
  disconnect(connection: ProviderConnection): Promise<void>;

  // Commands — server validates against capabilities before calling
  sendMessage(connection, input: MessageInput): Promise<void>;
  abort(connection): Promise<void>;
  listSessions?(connection): Promise<SessionSummary[]>;
  switchSession?(connection, sessionRef: string): Promise<SessionSnapshot>;
  newSession?(connection, options?: NewSessionOptions): Promise<SessionSnapshot>;
  getSnapshot?(connection): Promise<SessionSnapshot>;
  // Model / queue / etc. — optional per capabilities

  subscribe(connection, onEvent: (event: SessionDomainEvent) => void): () => void;
}

The server assigns each live connection an opaque connectionId. The UI never sees PI request IDs, JSONL, or Codex wire details.

6. WebSocket protocol (sketch)

One WebSocket per UI client. Messages are JSON objects with a type field. Use request/response correlation (id) for commands; use server-push for events.

6.1 Client → server (commands)

type Purpose
workspace.connect Connect repo/workspace with providerId, optional sessionRef
workspace.disconnect Disconnect connectionId
session.list List sessions for repo (provider + index merge on server)
session.switch Switch active session
session.create New session
message.send Prompt / steer / follow-up (mode in payload)
run.abort Abort active run
session.snapshot Fetch state + messages (reconnect)
preferences.get / preferences.update Desktop settings and index
provider.ui.respond Reply to provider UI prompt (extension UI, etc.)

6.2 Server → client (events)

type Purpose
connection.status connected / starting / error / exited + diagnostics
session.event SessionDomainEvent + connectionId
provider.ui.request Select / confirm / input / editor prompts
workspace.diff Git patch summary (server-computed)
error Correlated or global errors
Versioning Include protocolVersion in the first server message after connect. Bump major version when breaking message shapes; support one previous version during transition.

6.3 Example flow

UI → { type: "workspace.connect", id: "1", providerId: "pi", repoPath: "/path", sessionRef?: "…" }
UI ← { type: "connection.status", connectionId: "c-abc", state: "starting", … }
UI ← { type: "connection.status", connectionId: "c-abc", state: "connected", … }
UI ← { type: "session.event", connectionId: "c-abc", event: { type: "run.started", … } }
UI → { type: "message.send", id: "2", connectionId: "c-abc", text: "…", mode: "prompt" }
UI ← { type: "session.event", connectionId: "c-abc", event: { type: "message.streaming", … } }

7. Provider roadmap

Phase 1 — PI

Transport: subprocess pi --mode rpc, stdin/stdout JSONL (existing behavior).

  • Implement PiProvider by moving logic from electron/main.ts: spawn, JSONL reader, RPC queue, extension UI.
  • Map PI RPC → SessionDomainEvent inside the provider (today’s pi-session/adapter.ts).
  • Reach parity with current desktop: connect repo, sessions, prompt/steer/follow-up/abort, models, slash commands, extension UI.

Phase 2 — Codex Server

Transport: client to Codex Server (protocol per Codex docs; likely HTTP/WebSocket or similar — implement in CodexProvider).

  • Second provider in registry; per-repo or global default providerId: "codex".
  • Implement only shared verbs first: connect, send, abort, session list/switch if Codex exposes them.
  • Normalize streaming and tool events into SessionDomainEvent; document gaps in capability flags.
  • Do not assume PI session file paths or worktree layout unless Codex shares the same cwd model.

Phase 3 — Cursor

Transport: TBD (API, CLI, or hybrid). Design CursorProvider after Codex proves the abstraction.

  • Expect weaker parity: sessions may be indexed-only in sidebar with provider-native thread IDs.
  • Auth and secrets stay outside H3Code UI copy where possible (env, OS keychain, provider config).
  • UI gates features via ProviderCapabilities rather than hard-coded provider checks.

9. Data ownership

Data Owner H3Code Server
Messages / transcript Provider Cache for display only; refresh from provider on reconnect
Session files / IDs Provider Opaque sessionRef in API
Recent repos, indexed session metadata H3Code SQLite Discovery and sidebar; not authoritative for provider-native list
Git diff / worktrees Server (platform) Same for all providers using local repo cwd
API keys Provider config Never stored in H3Code UI state
Anti-pattern Adding a H3Code messages table or session store “for convenience” breaks the product boundary and complicates multi-provider sync.

10. Migration phases

  1. Extract agent-core — SessionDomainEvent, provider types, WebSocket message unions (no runtime change).
  2. Stand up Agent Server — localhost WebSocket, health check, PiProvider only.
  3. Switch desktop UI — replace window.h3code IPC invoke/event listeners with WS client; keep Electron for window + native dialogs.
  4. Delete PI logic from Electron main — main spawns server and optionally opens devtools bridge.
  5. Add CodexProvider — provider picker in settings; capability-gated UI.
  6. Add CursorProvider — after Codex validates the abstraction.

During transition, optional dual path (IPC + WS) is acceptable for one release; avoid long-term duplication.

11. Security and operations

  • Bind server to 127.0.0.1 only; reject non-local connections.
  • Use a random per-startup token or Unix domain socket path in user data dir; UI includes token on WebSocket connect.
  • Do not log message bodies or tool output at info level in production.
  • Validate all client payloads (schema) at the server boundary.
  • Electron remains responsible for secure native prompts; server receives only validated paths from trusted bridge or user-selected paths relayed by UI.
